## Build, package, install

```sh
make              # build lib{{project_name}}.so
make apk          # package and sign
make install      # install it (with adb on this phone: no prompt)
make run          # install, then start it (adb)
make logcat       # its log, and Android's crash lines (adb)
make console      # a CONSOLE build's Console, here in Termux (no adb)
                  # in it: ls, pull <path>, push <file>, logcat, libs
```

No Gradle, no Android Studio, no `classes.dex`, no Java in the build. A
compiler, `make`, and the NDK and SDK command-line pieces. It works on a phone.

```sh
make android-status   # what the build found on this host
make android-help     # every target and override
```

A build prints one short line as each step starts and says the flags once:

```
{{project_name}}: flags as before
squared release: flags as before
  cc   sq_app/src/app.cpp
  link lib{{project_name}}.so
```

When the flags changed (another `SQ_MIN_SDK`, `DEV_LOG=1`, `CONSOLE=app`) it
lists every one, a line each, marking what is `(new)` or `(gone)`, and
rebuilds what they affect. Warnings and errors print in full. `make V=1`
prints every command instead.

## adb on the phone itself

Without adb, `make install` hands the APK to Android's installer, which asks
every time, and nothing in Termux can read the app's log (an app reads only
its own). With Wireless Debugging (Android 11 and later, on Wi-Fi), Termux's
`adb` reaches the phone it runs on:

```sh
pkg install android-tools
make devices                      # what adb reaches, and the steps to connect
adb pair localhost:<pairing port> # once: Settings > Developer options >
                                  # Wireless debugging > Pair device with code
bash tools/device.sh connect      # each time it is turned on (or: connect <port>)
make run                          # install with no prompt, then start it
make logcat                       # the app's lines, a library that failed to
                                  # load, the crash summary
bash tools/device.sh run-as {{package_name}} cat files/crash-previous.txt
```

The pairing dialog closes when you leave it, so keep Termux beside it (split
screen or a floating window) while you type the code. Wireless Debugging turns
itself off when Wi-Fi does.

`make install` uses adb only for **this phone**: the attached device whose
build fingerprint matches the one Termux reads, and only when adb's server is
already running (it never starts one to look). Anything else, a tablet on USB
included, is used only when named: `make install DEVICE=<serial>`, with the
serial `make devices` shows (`SQ_ADB=termux-adb` for a USB device reached
through termux-adb). `run-as` needs a debuggable build: `DEV_LOG` and
`CONSOLE` builds are.

## Who owns what

| Path | Owner | On update |
|---|---|---|
| `sq_app/**` | you | never touched |
| `sq_android/**` | you | never touched |
| `Makefile`, `README.md`, `.gitignore` | you | never touched |
| `mk/**`, `sq_kit/**` | generator | rewritten |
| `.squared/**` | generator | rewritten |

`sq_android/` is seeded rather than generated on purpose. The manifest, the
resources and the platform entry point are all yours to change — that is the
expert escape hatch. You should not normally need it, because the defaults
work.

## Where to start

`sq_app/src/app.cpp`. It clears the screen to a slowly pulsing colour and
reacts to touch — enough to prove the whole chain works, and the first thing to
delete.

Note what `sq_app/` does **not** include: no `<android/...>`, no EGL, no GLES.
The platform layer calls into your `App`; the same class compiles under other
templates with a different platform layer. Keeping Android out of `sq_app/` is
worth defending as you add code.

## Rendering

The renderer is optional and swappable. `sq_android/entry.cpp` and
`sq_app/src/app.cpp` both guard their include with `__has_include`, so this
project builds and runs with no rendering kit — you get a black window and a
log line saying so.

With `kit.opengl` you get `sq::gl`: EGL context management and GLES 3.0.
Shaders are GLSL ES 3.00 (`#version 300 es`), which needs explicit precision
qualifiers in fragment shaders.

```sh
make gl-status
```

## Why the SDK version is not in the manifest

`AndroidManifest.xml` deliberately carries no `<uses-sdk>`. The levels are
passed to `aapt2` by the build, so retargeting never means editing a file:

```sh
make apk SQ_MIN_SDK=26 SQ_TARGET_SDK=35
```

`SQ_MIN_SDK` is more than a manifest entry. The code is compiled for that API
level and linked against that level's system libraries from the NDK, so a call
to anything newer fails the link instead of the device. The default, 22
(Android 5.1), gives one APK that runs on that and on everything after it.
The C++ runtime is linked into your library; the APK carries no
`libc++_shared.so`.

## One ABI

This host builds for `arm64-v8a`. Termux's clang targets aarch64 only, and
building four ABIs on a phone is not the use case. A desktop NDK can do more —
`make android-help` explains how.
