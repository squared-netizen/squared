## Build, package, install

With sqmake, the SDK's build tool (`pkg install sqmake`), from `build.lua`:

```sh
sqmake            # build/{{project_name}}.apk, signed and verified
sqmake install    # install it (with adb on this phone: no prompt)
sqmake run        # install, then start it (adb)
sqmake logcat     # its log, and Android's crash lines (adb)
sqmake devices    # what adb reaches, and how to connect
sqmake --debug install   # the build you debug with: the Console, DEV_LOG,
                         # debuggable (in build/debug, so switching rebuilds neither)
sqmake console    # a debug build's Console, here in the terminal (no adb):
                  # in it: ls, pull <path>, push <file>, logcat, libs,
                  # screens (the stack and what each screen keeps),
                  # dump sys (every system command; dump lists the groups)
```

`build`, `install`, `run` and `test` are sqmake's verbs, the same words in
every project; what they do on Android is said once, in squared's
`build/android.lua`, and a line in `build.lua` can say otherwise. The device
is reached through `tools/device.sh` (or what `app.device` names). Which
squared it builds with: the SDK's, installed (`pkg install squared`, the
newest unless `app.squared = "1.0.0"` names a version), or a `squared/` folder
of the workspace's own, for one that changes squared itself.
`sq/build/template.lua` says what each setting of `build.lua` does (the API
levels, the background service, the debug build's Console and log);
`.sqmake.lua` with `separate_debug = false` keeps the debug build in
`build/`. An app with `sq_app/names.json` or `sq_app/layouts/` needs
sqgui-gen on PATH for it (`pkg install sqgui`).

No Gradle, no Android Studio, no Java in the build, no make and no shell: a
compiler, sqmake, and apkpack. It works on a phone.

## adb on the phone itself

Without adb, `sqmake install` hands the APK to Android's installer, which
asks every time, and nothing in the terminal can read the app's log (an app
reads only its own). With Wireless Debugging (Android 11 and later, on Wi-Fi),
`adb` reaches the phone it runs on:

```sh
pkg install android-tools
sqmake devices                    # what adb reaches, and the steps to connect
adb pair localhost:<pairing port> # once: Settings > Developer options >
                                  # Wireless debugging > Pair device with code
bash tools/device.sh connect      # each time it is turned on (or: connect <port>)
sqmake run                        # install with no prompt, then start it
sqmake logcat                     # the app's lines, a library that failed to
                                  # load, the crash summary
bash tools/device.sh run-as {{package_name}} cat files/crash-previous.txt
```

The pairing dialog closes when you leave it, so keep the terminal beside it
(split screen or a floating window) while you type the code. Wireless
Debugging turns itself off when Wi-Fi does.

`sqmake install` uses adb only for **this phone**: the attached device whose
build fingerprint matches this one's, and only when adb's server is already
running (it never starts one to look). Anything else, a tablet on USB
included, is used only when named (`DEVICE=<serial> sqmake install`, the
serial `sqmake devices` shows). `run-as` needs a debuggable build: `sqmake
--debug` builds are.

## Layout

```text
sq_app/        your code — portable C++, no Android headers
sq_android/    the platform layer — manifest, resources, entry point
sq_kit/        kit-provided headers (generator-owned)
build.lua      yours: sqmake's build; includes sq/build/template.lua
sq/build/      the template's and each kit's build, in Lua (generator-owned)
tools/         device.sh: how the build reaches a device (adb, or Android's installer)
SQ-INF/        what this workspace is and was made from (square reads it)
```

## Who owns what

| Path | Owner | On update |
|---|---|---|
| `sq_app/**` | you | never touched |
| `sq_android/**` | you | never touched |
| `build.lua`, `README.md`, `.gitignore` | you | never touched |
| `sq/build/**`, `sq_kit/**` | generator | rewritten |
| `SQ-INF/**` | generator, then square | rewritten |

`sq_android/` is seeded rather than generated on purpose. The manifest, the
resources and the platform entry point are all yours to change — that is the
expert escape hatch. You should not normally need it, because the defaults
work.

## Where to start

`sq_app/src/main.cpp` and `sq_app/layouts/landing.json`: a screen that says
Hello and has a Quit button. `squared_main` pushes it; the build compiles the
layout file into `layouts::landing`. Add a screen by adding a layout file, a
model with `app.run<YourModel>()`. `sq_app/README.md` has the rest.

Note what `sq_app/` does **not** include: no `<android/...>`, no EGL, no GLES.
The platform layer runs your app through `sq::App`; the same code compiles
under other templates with a different platform layer. Keeping Android out of
`sq_app/` is worth defending as you add code.

## Rendering

The renderer is chosen when the framework is linked: `sq::graphics::Context`
always exists, and with no GLES backend the null one draws nothing, so this
project builds and runs without one — you get a black window and a log line
saying so.

With `kit.opengl` you get `sq::gl`: EGL context management and GLES 3.0.
Shaders are GLSL ES 3.00 (`#version 300 es`), which needs explicit precision
qualifiers in fragment shaders.

## Why the SDK version is not in the manifest

`AndroidManifest.xml` deliberately carries no `<uses-sdk>`. The levels are
given to apkpack by the build, so retargeting never means editing a file:
`app = {..., min_sdk = 28, target_sdk = 35}` in `build.lua`.

`min_sdk` is more than a manifest entry. The code is compiled for that API
level and linked against that level's system libraries from the sysroot, so a
call to anything newer fails the link instead of the device. The C++ runtime
is linked into your library; the APK carries no `libc++_shared.so`.

## One ABI

This builds for `arm64-v8a`, the phone's: the SDK's toolchain is one clang,
one libc++ and one sysroot for that target.

## Independence

This workspace does not depend on squared-pg. The generator is not on the build
path, is not referenced by build.lua, and does not need to be installed to
build, run or ship what it produced.
